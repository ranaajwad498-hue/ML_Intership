# Database Layer Documentation

This document describes the database layer of the application: how it's structured, why the tools were chosen, how to verify it's working, and how it fits into the broader system (including future ML prediction storage).

---

## 1. What ORM Means

**ORM** stands for **Object-Relational Mapper**. It's a technique (and usually a library) that lets you interact with a relational database using the objects and classes of your programming language instead of writing raw SQL.

In practice, an ORM:

- Maps a **database table** to a **Python class**.
- Maps a **table row** to an **instance** of that class.
- Maps **columns** to **class attributes**.
- Translates method calls like `.query()`, `.add()`, `.filter()` into the equivalent `SELECT`, `INSERT`, `UPDATE`, `DELETE` SQL statements behind the scenes.

Instead of writing:

```sql
SELECT * FROM users WHERE id = 1;
```

you write:

```python
db.query(User).filter(User.id == 1).first()
```

The ORM handles connection management, query generation, and converting SQL result rows back into Python objects.

---

## 2. Why SQLAlchemy Is Used

**SQLAlchemy** is the ORM chosen for this project. Reasons:

- **Maturity and stability** — it's the most widely used Python ORM/SQL toolkit, with a large community and long track record in production systems.
- **Two levels of abstraction** — it offers both a high-level ORM (classes/objects) and a lower-level Core (SQL expression language), so you can drop down to raw-ish SQL when needed without leaving the library.
- **Database-agnostic** — the same model code can target PostgreSQL, MySQL, SQLite, etc., with minimal changes, which is useful for local dev vs. production.
- **First-class FastAPI integration** — works cleanly with FastAPI's dependency injection system for managing sessions per request.
- **Migration support via Alembic** — schema changes can be version-controlled and applied incrementally.
- **Type safety with Pydantic** — SQLAlchemy models pair naturally with Pydantic schemas for request/response validation.

## 3. PostgreSQL Connection Process

The connection is configured through a database URL and a SQLAlchemy `engine`, which manages a pool of connections to PostgreSQL.

**`database.py`**

```python
from sqlalchemy import create_engine
from sqlalchemy.ext.declarative import declarative_base
from sqlalchemy.orm import sessionmaker
import os

DATABASE_URL = os.getenv(
    "DATABASE_URL",
    "postgresql://postgres:password@localhost:5432/app_db"
)

engine = create_engine(DATABASE_URL)

SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)

Base = declarative_base()
```

**Connection flow:**

1. `DATABASE_URL` is read from an environment variable (falls back to a local default).
2. `create_engine()` builds a connection pool — it does **not** connect immediately; connections are opened lazily on first use.
3. `SessionLocal` is a factory that produces new `Session` objects, each representing a "conversation" with the database for the duration of a request.
4. `Base` is the declarative base class that all ORM models inherit from, so SQLAlchemy knows which classes map to tables.

## 4. SQLAlchemy Model

Models are Python classes that map directly to PostgreSQL tables.

**`models.py`**

```python
from sqlalchemy import Column, Integer, String, Float, DateTime
from sqlalchemy.sql import func
from database import Base

class Record(Base):
    __tablename__ = "records"

    id = Column(Integer, primary_key=True, index=True)
    name = Column(String, nullable=False)
    value = Column(Float, nullable=True)
    created_at = Column(DateTime(timezone=True), server_default=func.now())
```

- `__tablename__` sets the actual PostgreSQL table name.
- `Column` definitions map to PostgreSQL column types (`Integer` → `INTEGER`, `String` → `VARCHAR`, etc.).
- `primary_key=True` creates the primary key constraint.
- `server_default=func.now()` lets PostgreSQL itself stamp the creation time.

## 5. Pydantic Schemas

Pydantic schemas define the shape of data going **in and out** of the API — separate from the SQLAlchemy model, which defines the shape of data **in the database**. This separation keeps internal DB fields (like autogenerated IDs) from leaking into request bodies unintentionally.

**`schemas.py`**

```python
from pydantic import BaseModel
from datetime import datetime
from typing import Optional

class RecordBase(BaseModel):
    name: str
    value: Optional[float] = None

class RecordCreate(RecordBase):
    pass

class RecordResponse(RecordBase):
    id: int
    created_at: datetime

    class Config:
        from_attributes = True  # allows creation from ORM objects
```

- `RecordCreate` — validates incoming POST data (no `id`, no `created_at`; those are server-generated).
- `RecordResponse` — validates outgoing data, including fields the DB generated.
- `from_attributes = True` lets Pydantic build the schema directly from a SQLAlchemy model instance.

## 6. Database Session

Each API request gets its own SQLAlchemy session, opened and closed via a FastAPI dependency.

**`database.py` (continued)**

```python
def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()
```

Usage in a route:

```python
from fastapi import Depends
from sqlalchemy.orm import Session

@app.get("/records")
def list_records(db: Session = Depends(get_db)):
    return db.query(Record).all()
```

This pattern guarantees:

- A **fresh session per request** (no state leaking between requests).
- The session is **always closed**, even if the request raises an exception, because of the `try/finally`.

## 7. CRUD Endpoints

**`main.py`**

```python
from fastapi import FastAPI, Depends, HTTPException
from sqlalchemy.orm import Session

import models, schemas
from database import engine, get_db

models.Base.metadata.create_all(bind=engine)

app = FastAPI()

# CREATE
@app.post("/records", response_model=schemas.RecordResponse)
def create_record(record: schemas.RecordCreate, db: Session = Depends(get_db)):
    db_record = models.Record(**record.dict())
    db.add(db_record)
    db.commit()
    db.refresh(db_record)
    return db_record

# READ (list)
@app.get("/records", response_model=list[schemas.RecordResponse])
def list_records(db: Session = Depends(get_db)):
    return db.query(models.Record).all()

# READ (single)
@app.get("/records/{record_id}", response_model=schemas.RecordResponse)
def get_record(record_id: int, db: Session = Depends(get_db)):
    record = db.query(models.Record).filter(models.Record.id == record_id).first()
    if not record:
        raise HTTPException(status_code=404, detail="Record not found")
    return record

# UPDATE
@app.put("/records/{record_id}", response_model=schemas.RecordResponse)
def update_record(record_id: int, updated: schemas.RecordCreate, db: Session = Depends(get_db)):
    record = db.query(models.Record).filter(models.Record.id == record_id).first()
    if not record:
        raise HTTPException(status_code=404, detail="Record not found")
    record.name = updated.name
    record.value = updated.value
    db.commit()
    db.refresh(record)
    return record

# DELETE
@app.delete("/records/{record_id}")
def delete_record(record_id: int, db: Session = Depends(get_db)):
    record = db.query(models.Record).filter(models.Record.id == record_id).first()
    if not record:
        raise HTTPException(status_code=404, detail="Record not found")
    db.delete(record)
    db.commit()
    return {"detail": "Record deleted"}
```

## 8. Database Status Endpoint

A lightweight health-check endpoint confirms the app can actually reach PostgreSQL, not just that the app process is alive.

```python
from sqlalchemy import text

@app.get("/db-status")
def db_status(db: Session = Depends(get_db)):
    try:
        db.execute(text("SELECT 1"))
        return {"status": "ok", "database": "connected"}
    except Exception as e:
        return {"status": "error", "database": "unreachable", "detail": str(e)}
```

This is useful for:
- Container orchestration health checks (Docker/Kubernetes liveness probes).
- Quick manual debugging ("is the app up but the DB down?").

## 10. How Records Were Verified in PostgreSQL

After exercising the API (creating a few records via `POST /records`), the underlying table was checked directly using `psql`:

```bash
psql -U postgres -d app_db
```

```sql
-- Confirm the table exists and its structure
\d records

-- Confirm the rows created via the API are actually persisted
SELECT id, name, value, created_at FROM records ORDER BY id;
```

Example output:

```
 id |     name      | value |         created_at
----+---------------+-------+-----------------------------
  1 | sensor_temp_1 |  23.5 | 2026-08-20 09:15:32.12+00
  2 | sensor_temp_2 |  19.8 | 2026-08-20 09:16:01.44+00
(2 rows)
```

This confirms:
- The `POST` endpoint is actually committing to PostgreSQL (not just returning an in-memory object).
- `created_at` is being populated by the database server default, not the application.
- Row values match exactly what was submitted through the API, verifying the ORM's field mapping is correct end-to-end.

A row was also updated and deleted through the API, then re-checked with the same `SELECT` query to confirm `PUT` and `DELETE` operations were reflected in PostgreSQL, not just in the API's response payload.

## 11. How This Database Layer Will Later Store ML Prediction Results

The current `Record` model is intentionally generic, but the same pattern — SQLAlchemy model + Pydantic schema + session dependency + CRUD routes — will extend naturally to store machine learning outputs. The planned approach:

**A new model for predictions:**

```python
class Prediction(Base):
    __tablename__ = "predictions"

    id = Column(Integer, primary_key=True, index=True)
    input_record_id = Column(Integer, ForeignKey("records.id"), nullable=True)
    model_name = Column(String, nullable=False)
    model_version = Column(String, nullable=False)
    prediction = Column(String, nullable=False)   # or JSON/Float depending on output type
    confidence = Column(Float, nullable=True)
    created_at = Column(DateTime(timezone=True), server_default=func.now())
```

**How it fits the existing layer:**

- **Foreign key linkage** — `input_record_id` ties a prediction back to the source data it was computed from, so results remain traceable.
- **Model metadata** — `model_name` and `model_version` are stored alongside each prediction, which matters once multiple model versions are deployed and predictions need to be compared or audited.
- **Same session/dependency pattern** — a new `POST /predictions` endpoint would accept a record ID, run inference, and persist the result using the same `get_db()` session dependency already in place.
- **Same schema separation** — a `PredictionCreate` / `PredictionResponse` pair in `schemas.py` keeps prediction request/response validation consistent with the rest of the API.
- **Same verification approach** — predictions written via the API would be checked directly in `psql` (`SELECT * FROM predictions`) the same way `records` was verified, confirming inference results are durably persisted rather than only returned transiently in the HTTP response.

In short, the ML prediction table is not a separate system — it reuses the exact connection, session, and CRUD conventions already established here, just with a schema shaped around model outputs instead of raw input records.
